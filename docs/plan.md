# Daily Study 기획서 (초안, 컨펌 대기)

작성일: 2026-10-31

## 1. 목표

백엔드 개발자가 매일 실무 시나리오형 문제와 CS·아키텍처 개념형 문제를 서술형으로 풀고,
LLM 감독관에게 채점과 학습 피드백을 받는 macOS·Windows 데스크톱 앱을 만든다.

### 완료 기준

- 앱을 실행하면 오늘의 문제 2~3개가 준비되어 있다.
- 답안을 제출하면 점수, 모범 답안, 잘한 점, 부족한 점, 추가 학습 주제가 표시된다.
- 원하는 주제·유형·난이도를 골라 추가 문제를 풀 수 있다.
- 이미 출제된 문제와 중복되는 문제는 출제되지 않는다.
- 지난 풀이 기록과 약점 통계를 볼 수 있다.
- 문제를 직접 입력하거나 LLM에게 생성을 요청해서 문제 은행에 추가할 수 있다.
- LLM 실행기로 `claude -p` 와 `codex exec` 중 하나를 설정에서 고를 수 있다.
- macOS와 Windows의 새 머신에서 설치 문서만 보고 설치를 끝낼 수 있다.

### 범위에서 제외하는 것

- 기술 커뮤니케이션 유형(비개발자 설명, 장애 회고 작성)
- 여러 사용자, 서버, 계정 동기화
- Linux 빌드
- 코드 서명과 자동 업데이트

### 확정된 결정 사항

| 항목 | 결정 |
|---|---|
| 지원 OS | macOS, Windows |
| 데이터 저장 | JSON 파일 |
| 약점 재출제 | 같은 쟁점이라도 상황이 다르면 허용 |
| LLM 문제 생성 시점 | 앱을 실행할 때 백그라운드에서 오늘과 내일 분량을 미리 생성 |
| 초기 문제 은행 난이도 | 주니어 14, 미들 28, 시니어 14 |

## 2. 문제 체계

### 2.1 두 가지 문제 형식

| 형식 | 분류 축 1 | 분류 축 2 |
|---|---|---|
| 시나리오형 | 시나리오 유형 7개 | 스택 주제 7개 |
| 개념형 | 개념 유형 5개 | 스택 주제 7개 |
| 단답형 | 단답형 유형 3개 | 스택 주제 7개 |

- **시나리오 유형:** 장애 진단, 설계 트레이드오프, 데이터 정합성과 동시성, 성능과 확장,
  마이그레이션과 레거시 개선, 설계 리뷰, 관측성과 운영
- **개념 유형:** 원리 설명, "왜" 질문, 비교, 계층 관통, 아키텍처 원칙
- **단답형 유형:** 용어와 정의, 동작 규칙, 상황 적용
- **스택 주제:** Kotlin/Spring, Kafka, MySQL/PostgreSQL, DynamoDB, 분산 시스템 공통, 캐시, API와 아키텍처
- **코드 없음:** 모든 문제는 글로만 쓴다. 문제 본문과 요구 항목에 코드 블록이나 코드 조각을 넣지 않고, 코드가 하는 일은 처리 순서와 조건으로 풀어 쓴다. 코드 리뷰 유형은 이 규칙에 따라 설계 리뷰(글로 쓴 처리 흐름에서 결함 찾기)로 바뀌었다. 예전에 코드 리뷰로 저장된 문제와 풀이는 그대로 남는다.

### 2.2 난이도

| 난이도 | 기대 수준 |
|---|---|
| 주니어 | 개념을 정확하게 설명하고, 흔한 실수를 피하는 수준 |
| 미들 | 실무 제약 안에서 원인을 찾고 해결책을 고르며, 그 근거를 설명하는 수준 |
| 시니어 | 트레이드오프를 비교하고, 장애·운영·조직 비용까지 고려해서 결정하는 수준 |

문제 하나는 난이도 하나를 가진다. 같은 상황을 난이도만 바꿔 다시 내는 것은 중복으로 본다(2.5 참고).

### 2.3 문제 구조

모든 문제는 같은 구조를 따른다. 채점 기준과 모범 답안은 답안을 제출하기 전까지 화면에 표시하지 않는다.

```
상황           구체적인 수치·환경·제약
요구           번호를 붙인 답변 항목
권장 분량      예: 600~1000자
-- 제출 전 비공개 --
채점 기준      필수 / 가점 / 감점 / 흔한 오답
모범 답안
연관 학습 주제
```

### 2.4 유형별 채점 관점

시나리오 유형마다 공통 채점 관점을 고정한다. 관점별 점수를 누적해서 약점 통계를 만든다.

| 유형 | 채점 관점 |
|---|---|
| 장애 진단 | 가설의 폭, 조사 순서의 근거, 즉시 완화책과 근본 해결책의 구분, 재발 방지 |
| 설계 트레이드오프 | 선택지 나열, 평가 기준 명시, 제약 반영, 결정을 바꿀 조건 |
| 데이터 정합성과 동시성 | 실패 시나리오의 정확성, 보장 수준 명시, 방어책의 구체성, 데이터 보정 |
| 성능과 확장 | 측정 근거, 수치로 한 용량 추정, 단계별 대응, 비용 |
| 마이그레이션과 레거시 개선 | 단계 분할, 단계별 롤백 가능성, 공존 기간의 호환성, 전환 검증 |
| 설계 리뷰 | 결함 발견 수, 심각도 순서, 수정안의 구체성, 결함이 드러나는 상황 설명 |
| 관측성과 운영 | 사용자 영향 기준 지표, 알람의 실행 가능성, 잡음 감소, 대응 절차 |

개념형은 정확성, 깊이(원리까지 내려갔는지), 연결(다른 개념과의 관계), 실무 적용의 4개 관점으로 채점한다.

### 2.5 중복 방지

중복의 정의: **상황과 요구가 사실상 같은 문제**. 수치나 고유 명사만 바꾼 문제, 난이도만 바꾼 문제도 중복으로 본다.

3단계로 막는다.

1. **생성 단계:** LLM에게 문제 생성을 요청할 때, 같은 주제의 기존 문제 요약(제목과 핵심 쟁점 한 줄)을 함께 넘기고 겹치지 않게 만들라고 지시한다.
2. **저장 단계:** 새 문제의 핵심 쟁점 키워드와 기존 문제를 비교해 유사도가 기준을 넘는 후보를 찾는다. 후보가 있으면 LLM에게 중복 여부를 판정하게 하고, 중복이면 버리고 다시 생성한다.
3. **출제 단계:** 한 번 출제된 문제는 다시 출제하지 않는다. 약점 재출제는 같은 쟁점을 **다른 상황**으로 묻는 새 문제를 만들어서 한다.

## 3. 출제 방식

### 3.1 오늘의 문제

- 기본 구성은 시나리오형 1문제와 개념형 1문제다. 설정에서 개념형을 1문제 더 추가해 3문제로 바꿀 수 있다.
- 이 구성과 별도로 단답형 3문제를 매일 서로 다른 스택 주제에서 낸다. 단답형은 LLM 이 정답, 부분 정답, 오답으로 판정하고 각각 100점, 50점, 0점을 준다. 힌트, 미루기, 약점 재출제는 적용하지 않는다. 단답형이 생기기 전에 정해진 오늘의 문제에는 단답형 3문제를 덧붙인다.
- 시나리오 유형은 요일별로 돌린다(월 장애 진단 → 일 관측성과 운영).
- 개념형은 시나리오형과 다른 스택 주제에서 고른다.
- 난이도는 설정의 기본 난이도를 따른다.
- 문제를 고르는 순서: 문제 은행에서 아직 출제되지 않은 문제 → 없으면 LLM 신규 생성.
- 문제 은행에서 고를 때는 켜 둔 주제 가운데 가장 오래전에 출제된 주제를 먼저 고르고, 같은 주제 안에서는 검토된 문제를 먼저 고른다. 직접 추가한 주제처럼 검토된 문제가 없는 주제도 차례가 돌아오게 하기 위해서다.
- LLM 생성은 앱을 실행할 때 백그라운드에서 오늘과 내일 분량을 미리 만들어 둔다. 문제를 열 때 기다리지 않게 하기 위해서다.
- 약점 재출제: 관점별 점수가 낮았던 주제는 3일 뒤, 7일 뒤에 변형 문제를 오늘의 문제에 섞는다.

### 3.2 추가 풀이

오늘의 문제와 별도로, 형식·유형·스택 주제·난이도를 골라 문제를 더 받을 수 있다. 출제 순서는 오늘의 문제와 같다.

### 3.3 문제 출처

| 출처 | 설명 |
|---|---|
| 문제 은행 | 사람이 검수한 문제. 초기 56문제(시나리오형 28, 개념형 28 / 주니어 14, 미들 28, 시니어 14)를 저장소에 포함한다. |
| 변형 생성 | 기존 문제의 쟁점을 다른 상황으로 바꿔 만든 문제. 약점 재출제에 쓴다. |
| 신규 생성 | 문제 은행이 비었거나 사용자가 요청한 주제에 대해 새로 만든 문제. 검증 단계를 통과해야 저장한다. |
| 직접 입력 | 사용자가 앱에서 직접 쓴 문제. 채점 기준을 비워 두면 LLM이 초안을 만들고 사용자가 확인한다. |

LLM이 생성한 문제에는 출처 표시를 남긴다. 사용자가 "검수 완료"를 누르면 문제 은행 문제로 승격된다.

### 3.4 사용자 피드백 반영

사용자는 문제의 품질과 출제 방식에 피드백을 남길 수 있고, 이후 문제 생성에 그 피드백이 반영된다.

| 피드백 종류 | 남기는 곳 | 내용 |
|---|---|---|
| 문제 피드백 | 채점 결과 화면, 문제 은행 화면 | 평가(좋음/아쉬움), 사유 태그(모호함, 너무 쉬움, 너무 어려움, 비현실적, 채점 기준 오류, 기존 문제와 비슷함), 자유 서술 |
| 출제 방식 피드백 | 피드백 화면 | 자유 서술. 적용 범위로 전체 또는 특정 형식·유형·주제·난이도를 고를 수 있다. 예: "설계 리뷰 문제는 처리 단계를 더 잘게 나눠서" |

반영 방법:
- 문제를 생성하거나 변형할 때, 적용 범위가 맞는 피드백을 최신순으로 최대 20건 골라 생성 요청에 함께 넘긴다. skill은 피드백을 "출제 지침"으로 취급하고, 기본 규칙(문제 구조, 중복 금지)과 충돌하면 기본 규칙을 따른다.
- "아쉬움" 평가를 받은 문제 은행 문제는 출제 후보에서 뒤로 미룬다. "채점 기준 오류" 태그가 붙은 문제는 검수 대기 상태로 되돌린다.
- 피드백 화면에서 지난 피드백을 보고, 더 이상 반영하지 않을 피드백은 비활성화한다.

## 4. 화면

### 4.1 화면 목록

| 화면 | 역할 |
|---|---|
| 오늘 | 오늘의 문제 목록, 문제별 진행 상태(미풀이/작성 중/채점 중/완료) |
| 문제 풀이 | 문제 확인, 답안 작성, 제출 |
| 채점 결과 | 점수, 관점별 점수, 잘한 점, 부족한 점, 모범 답안, 추가 학습 주제 |
| 추가 풀이 | 형식·유형·주제·난이도를 골라 문제 받기 |
| 기록 | 지난 풀이 목록(날짜·주제·유형·난이도·점수 필터), 관점별·주제별 약점 통계 |
| 문제 은행 | 문제 목록, 직접 추가, LLM 생성 요청, 검수 상태 관리 |
| 피드백 | 출제 방식 피드백 작성, 지난 피드백 목록과 활성/비활성 전환 |
| 설정 | LLM 실행기(Claude/Codex), 기본 난이도, 하루 서술형 문제 수, 데이터 폴더 위치 |

### 4.2 문제 풀이 화면

화면을 좌우로 나눠 문제를 보면서 답안을 쓸 수 있게 한다.

```
┌──────────────────────────────────────────────────────────────────┐
│ ← 오늘   [시나리오형] 데이터 정합성과 동시성 · Kafka · 미들           │
├───────────────────────────────┬──────────────────────────────────┤
│ 상황                           │ 답안                     612/1000자│
│  주문 서비스는 @Transactional   │ ┌──────────────────────────────┐ │
│  메서드 안에서 ...              │ │ ① (a)는 커밋 이후 ...          │ │
│                               │ │                              │ │
│ 요구                           │ │                              │ │
│  ① (a)와 (b)의 발생 경로        │ │                              │ │
│  ② 근본적인 해결 설계           │ └──────────────────────────────┘ │
│  ③ 컨슈머가 지켜야 할 조건       │ 자동 저장됨 · 09:12               │
│                               │ [ 미리보기 ]        [ 제출하기 ]   │
└───────────────────────────────┴──────────────────────────────────┘
```

- 답안은 마크다운으로 쓰고, 미리보기로 렌더링 결과를 확인한다.
- 작성 중인 답안은 자동 저장한다. 앱을 껐다 켜도 남아 있다.
- 권장 분량 대비 글자 수를 표시한다.
- 제출 후에는 답안을 수정할 수 없다. 같은 문제를 다시 풀려면 "다시 풀기"로 새 풀이를 만든다.

### 4.3 채점 결과 화면

```
┌──────────────────────────────────────────────────────────────────┐
│ 72점 / 100      필수 항목 3/4 충족                                 │
│ 실패 시나리오 ████████░░  보장 수준 ██████░░░░                     │
│ 방어책       ███████░░░  데이터 보정 ███░░░░░░░                    │
├──────────────────────────────────────────────────────────────────┤
│ [잘한 점] [부족한 점] [모범 답안] [내 답안 비교] [추가 학습]          │
├──────────────────────────────────────────────────────────────────┤
│ 부족한 점                                                         │
│  • 컨슈머 멱등성을 언급하지 않았습니다. outbox 릴레이는 ...          │
│    → 내 답안의 해당 문장: "outbox를 쓰면 정확히 한 번 ..."          │
└──────────────────────────────────────────────────────────────────┘
```

- 피드백은 내 답안의 어느 문장에 대한 것인지 인용해서 보여 준다.
- "내 답안 비교" 탭은 내 답안과 모범 답안을 좌우로 나란히 보여 준다.
- 추가 학습 항목은 키워드와 "왜 필요한지" 한 줄, 참고 자료 검색어로 구성한다.

### 4.4 공통 UX 기준

모든 화면이 다음 상태를 갖춘다.

| 상태 | 처리 |
|---|---|
| 불러오는 중 | 목록과 본문은 스켈레톤, 버튼 동작은 버튼 안 스피너로 표시한다. |
| LLM 작업 중 | 진행 단계 문구("문제를 읽는 중", "채점 기준과 대조하는 중")와 경과 시간을 표시하고, 취소 버튼을 둔다. 작업은 화면을 벗어나도 계속되며, 상단 작업 표시줄에서 진행 상태를 볼 수 있다. |
| 완료·실패 알림 | 화면 오른쪽 아래 토스트로 알린다. 실패 토스트에는 "다시 시도" 버튼을 둔다. |
| 비어 있음 | 무엇을 하면 되는지 안내 문구와 다음 행동 버튼을 표시한다. |
| 오류 | 사람이 읽을 수 있는 원인, 다시 시도 버튼, 접을 수 있는 원문 로그를 표시한다. |

- 작업 중인 버튼은 비활성화해서 중복 제출을 막는다.
- 제출과 삭제처럼 되돌릴 수 없는 동작은 확인 대화상자를 거친다.
- 단축키: `Cmd/Ctrl + Enter` 제출(확인 대화상자 표시), `Cmd/Ctrl + S` 임시 저장.
- 라이트·다크 테마는 OS 설정을 따른다.

## 5. LLM 연동 표준

### 5.1 원칙

출제·채점 규칙의 원본은 저장소 안의 **skill 파일 하나**로 둔다. 앱, Claude, Codex가 모두 같은 파일을 읽는다.
규칙을 바꾸려면 skill 파일만 고치면 된다.

```
daily-study/
  skills/
    daily-study-question-author/   문제 생성·변형·중복 판정
      SKILL.md
      references/                  분류 체계, 난이도 기준, 채점 관점, 샘플 문제
    daily-study-grader/            채점·피드백·학습 추천
      SKILL.md
      references/
  schemas/                         문제·채점 결과 JSON Schema
```

### 5.2 실행 방식

| 실행기 | 명령 | 출력 강제 방법 |
|---|---|---|
| Claude | `claude -p "<요청>" --output-format json --json-schema <schema>` | `--json-schema` (설치된 2.1.316에서 확인) |
| Codex | `codex exec "<요청>" --output-schema <file> -o <결과 파일>` | `--output-schema` (설치된 0.153.0에서 확인) |

- 앱은 실행기에 skill을 사용하라는 요청과 입력 데이터(문제, 답안, 기존 문제 요약)를 넘긴다.
- 결과는 JSON Schema로 검증한다. 검증에 실패하면 한 번 재시도하고, 그래도 실패하면 오류 화면에 원문을 보여 준다.
- 실행기는 읽기 전용으로 실행한다. 파일 쓰기와 명령 실행 도구는 허용하지 않고, 저장은 앱이 한다.
- 채점은 30초에서 2분 정도 걸리므로 백그라운드로 실행하고, 진행 중에도 다른 화면을 쓸 수 있게 한다.
- Windows에서는 CLI가 `claude.cmd`처럼 래퍼 스크립트로 설치되므로, 실행 파일 경로를 OS별로 찾는 모듈을 하나 두고 모든 호출이 그 모듈을 거치게 한다. 설정 화면에서 실행 파일 경로를 직접 지정할 수도 있게 한다.
- Codex는 Windows에서 WSL 사용을 권장하는 경우가 있으므로, 구현 단계에서 네이티브 Windows 실행 여부를 확인하고 설치 문서에 반영한다.

### 5.3 터미널에서도 같은 규칙으로 사용

설치 스크립트가 skill 폴더를 Claude와 Codex의 사용자 skill 위치에 연결한다.
macOS에서는 심볼릭 링크를 쓰고, Windows에서는 관리자 권한 없이 만들 수 있는 디렉터리 정션을 쓴다. 정션을 만들 수 없으면 복사하고, `npm run setup`을 다시 실행하면 갱신되게 한다.
그러면 앱 없이 터미널에서 "Kafka 시니어 시나리오 문제 하나 만들어 줘"라고 해도 같은 규칙으로 문제가 생성된다.
Codex의 사용자 skill 경로는 구현 단계에서 설치된 버전 기준으로 확인한다.

## 6. 데이터 저장

JSON 파일로 저장한다. 기본 위치는 OS의 문서 폴더 아래 `DailyStudy/` 이고(macOS `~/Documents/DailyStudy`, Windows `%USERPROFILE%\Documents\DailyStudy`), 설정에서 바꿀 수 있다.
설치된 앱은 저장소 위치를 알 수 없으므로 저장소 안이 아니라 문서 폴더를 기본값으로 둔다.

```
data/
  questions/<question-id>.json    문제 (채점 기준과 모범 답안 포함)
  attempts/<attempt-id>.json      풀이 (답안, 제출 시각, 채점 결과)
  feedback/<feedback-id>.json     문제 피드백과 출제 방식 피드백
  daily/<YYYY-MM-DD>.json         그날 출제된 문제 목록
  settings.json
```

- SQLite 대신 JSON 파일을 쓰는 이유: 네이티브 모듈 빌드가 필요 없어 설치가 단순하고, 문제 은행을 git으로 관리하기 쉽다. 예상 데이터 규모(문제 수천 개 이하)에서는 성능 문제가 없다.
- 초기 문제 은행 56문제는 저장소의 `seed/` 폴더에 두고 앱에 함께 묶는다. 첫 실행 때 `questions/`로 복사한다.
- 파일 경로는 항상 `path.join`으로 조합하고, 파일 이름에는 Windows에서 쓸 수 없는 문자(`:` 등)를 넣지 않는다.

## 7. 기술 스택

| 영역 | 선택 |
|---|---|
| 앱 | Electron + TypeScript, electron-vite |
| UI | React, Tailwind CSS, react-markdown(코드 하이라이트 포함) |
| 검증 | JSON Schema (ajv) |
| 패키징 | electron-builder로 macOS `.dmg`, Windows NSIS 설치 파일(`.exe`) 생성 |
| 빌드 자동화 | GitHub Actions에서 macOS·Windows 러너로 각각 빌드 (Windows 설치 파일을 macOS에서 교차 빌드하는 방식은 불안정해서 쓰지 않는다) |
| 테스트 | Vitest (출제 규칙, 중복 판정, 스키마 검증) |

LLM 실행기 호출은 Electron 메인 프로세스에서만 하고, 화면 쪽에는 IPC로 결과만 전달한다.

## 8. 설치 방법 (문서로 제공할 내용)

공통 단계와 OS별 단계를 나눠서 문서화한다.

**공통**
1. 준비물: Node.js 22.12 이상, Claude Code 또는 Codex CLI 설치 및 로그인
2. `git clone` 또는 폴더 복사 후 `npm install`
3. `npm run setup`: skill 연결, 실행기 설치 여부와 로그인 상태 점검
4. 개발 모드 실행: `npm run dev`
5. 앱에서 설정 → 실행기를 고르고 "연결 테스트"를 누른다.

**macOS**
- 빌드: `npm run dist:mac` → `release/` 의 `.dmg` 를 열어 응용 프로그램 폴더로 이동
- 서명하지 않은 앱이므로 처음 실행할 때 "시스템 설정 → 개인정보 보호 및 보안"에서 실행을 허용한다.

**Windows**
- 빌드: `npm run dist:win` → `release/` 의 설치 파일(`.exe`) 실행
- 서명하지 않은 앱이므로 SmartScreen 경고가 나오면 "추가 정보 → 실행"을 누른다.
- PowerShell 실행 정책 때문에 `npm` 스크립트가 막히면 해결 방법을 문서에 함께 적는다.

빌드 없이 쓰고 싶은 경우를 위해 GitHub Actions가 만든 설치 파일을 내려받는 방법도 문서에 적는다.
