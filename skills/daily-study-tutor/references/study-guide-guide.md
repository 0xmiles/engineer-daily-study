# 학습 노트 작성 가이드

학습 노트는 사용자가 앱 안에서 처음부터 끝까지 읽고 공부하는 자료다. 검색 결과 요약이 아니라, 좋은 선배가 면접 준비하는 후배에게 설명해 주듯 쓴다.

## 난이도별 깊이

| 난이도 | 기대 수준 |
|---|---|
| `junior` | 개념의 정의와 존재 이유, 기본 동작을 정확하게 설명한다. 대표적인 사용 예를 든다. |
| `middle` | 내부 동작 원리와 설정 값이 동작에 주는 영향, 장애 상황에서 무슨 일이 생기는지까지 다룬다. |
| `senior` | 트레이드오프와 대안 비교, 규모가 커질 때의 한계, 운영 중 판단 기준까지 다룬다. |

난이도를 알 수 없으면 `middle` 로 쓴다.

## 필드별 규칙

### `summary`

3~5문장. 이 키워드가 무엇이고, 왜 중요하며, 사용자가 놓친 지점(`reason`)이 무엇인지 한 번에 잡히게 쓴다. `recommendations` 가 비어 있으면 놓친 지점 대신 `questions` 같은 문제를 풀 때 이 키워드의 어떤 점을 알아야 하는지 쓴다. 둘 다 비어 있으면(사용자가 직접 추가한 키워드) 실무와 면접에서 이 키워드의 어떤 점을 알아야 하는지 쓴다.

### `sections`

4~6개. 아래 흐름을 기본으로 하되, 키워드에 맞지 않는 섹션은 빼거나 바꾼다.

1. 개념: 정의와 등장 배경. 무엇을 해결하려고 생겼는지.
2. 동작 원리: 내부에서 실제로 일어나는 순서. 단계가 있으면 번호 목록으로 쓴다.
3. 실무 적용: 설정, 코드, 명령 예시. 코드는 언어를 밝힌 코드 블록으로 쓰고, 프로젝트 맥락에 맞게 Kotlin·Spring 예시를 우선한다.
4. 트레이드오프와 대안: 언제 쓰고 언제 쓰지 않는지, 비교 대상이 있으면 표로 비교한다.
5. 면접에서 설명하는 법: 이 키워드를 묻는 질문에 1분 안에 답한다면 어떤 순서로 무엇을 말할지.

- `heading` 은 짧은 명사구로 쓴다. 번호를 붙이지 않는다.
- `body` 는 마크다운이다. 문단, 목록, 표, 코드 블록을 쓸 수 있다. 제목(`#`)은 쓰지 않는다.
- 섹션 하나는 2~5문단 분량으로, 앞 섹션을 읽었다고 가정하고 이어서 쓴다.
- `reason` 에 나온 빈틈은 어느 섹션에서든 반드시 직접 다룬다.
- `questions` 의 `keyIssues` 와 `requiredPoints` 중 이 키워드에 해당하는 내용도 어느 섹션에서든 다룬다. 다만 문제의 결론이 아니라 그 결론을 내리는 데 필요한 원리로 쓴다.

### `pitfalls`

2~5개. 이 키워드에서 자주 틀리는 오해나 실수를 "~라고 생각하기 쉽지만, 실제로는 ~다." 형태로 한 문장씩 쓴다. `reason` 에 드러난 오해가 있으면 가장 먼저 쓴다.

### `selfCheck`

3~5개. 노트를 읽은 뒤 스스로 답해 볼 질문이다.

- 정의를 묻는 질문 하나, 동작 원리나 상황 판단을 묻는 질문을 나머지로 둔다. "~하면 어떻게 될까요?"처럼 상황을 주는 질문을 우선한다.
- `question` 은 노트 본문을 그대로 베껴 답할 수 있는 질문이 아니라, 본문을 이해했는지 확인하는 질문이다.
- `answer` 는 2~4문장의 모범 답이다. 마크다운을 쓸 수 있다.

### `relatedKeywords`

2~6개. 이 키워드를 이해한 다음 이어서 공부하면 좋은 키워드다. 이 키워드 자체나 표기만 다른 같은 개념은 넣지 않는다.
