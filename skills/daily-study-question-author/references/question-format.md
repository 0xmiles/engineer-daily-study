# 문제 작성 규칙

## 필드별 규칙

| 필드 | 규칙 |
|---|---|
| `title` | 문제의 핵심 상황을 한 줄로 쓴다. 정답을 암시하지 않는다. 예: "주문 저장과 이벤트 발행 사이의 불일치" (O), "Outbox 패턴 적용하기" (X) |
| `situation` | 마크다운. 구체적인 수치(트래픽, 데이터 규모, 지연 시간), 환경(스택, 배포 형태, 인스턴스 수), 제약(마감, 팀 규모, 비용)을 넣는다. 관찰된 증상은 사실로만 쓰고 원인을 쓰지 않는다. 개념형은 질문 본문을 여기에 쓴다. |
| `requirements` | 답해야 할 항목. 항목마다 하나의 질문만 담는다. 번호는 앱이 붙이므로 쓰지 않는다. |
| `recommendedLength` | 한국어 글자 수 기준. `difficulty.md` 의 범위를 따른다. |
| `keyIssues` | 이 문제가 묻는 핵심 쟁점 2~4개. 중복 판정에 쓰이므로 구체적으로 쓴다. 예: "DB 커밋과 메시지 발행의 이중 쓰기", "컨슈머 멱등 처리" |
| `rubric.required` | 반드시 들어가야 할 항목. `point` 는 짧은 이름, `explanation` 은 무엇을 쓰면 충족인지와 왜 필요한지. 대안이 여러 개면 인정하는 대안을 모두 적는다. |
| `rubric.bonus` | 있으면 더 좋은 항목. 2~4개. |
| `rubric.deductions` | 틀린 주장이나 위험한 해결책. `explanation` 에 왜 틀렸는지 쓴다. 1~3개. |
| `rubric.commonMistakes` | 감점까지는 아니지만 자주 빠뜨리거나 헷갈리는 점. 1~3개. |
| `perspectives` | `perspectives.md` 의 값을 그대로 쓴다. |
| `modelAnswer` | 마크다운. `requirements` 순서대로 소제목을 달고 답한다. 필수 항목을 모두, 가점 항목을 대부분 포함한다. 권장 분량의 최대치를 크게 넘기지 않는다. |
| `relatedStudyTopics` | 이 문제를 더 깊게 공부할 때 찾아볼 주제 3~5개. 검색어로 쓸 수 있는 구체적인 이름으로 쓴다. |

## 시나리오형 복합 구조 규칙

시나리오형은 실제 장애나 설계 결정처럼 **여러 기술이 얽히고 원인이 여러 겹**인 상황을 다룬다. 아래 두 조건을 모두 지킨다. 난이도별 강도는 `difficulty.md` 의 "시나리오형 복합도" 표를 따른다.

### 조건 1. 여러 기술 계층이 얽힌다

- `situation` 에 기술 계층이 2개 이상 등장한다. 계층은 애플리케이션 런타임(Kotlin/Spring, 스레드·커넥션 풀), 메시징(Kafka, SQS), 저장소(MySQL/PostgreSQL, DynamoDB), 캐시(Redis, 로컬 캐시), 네트워크와 API(게이트웨이, 로드밸런서, 서비스 간 호출), 배포와 인프라(오토스케일링, 컨테이너 자원)로 나눈다.
- `topic` 은 문제의 중심 계층이다. 다른 계층도 배경 설명에 그치지 않고, 원인이나 해결에 실제로 관여해야 한다. 그 계층의 설정과 수치(타임아웃, 풀 크기, 파티션 수, TTL 등)를 함께 준다.
- 원인이나 해결이 계층 경계를 넘나들어야 한다. 한 계층만 고쳐서 끝나는 문제는 시나리오형으로 내지 않는다.

### 조건 2. 원인이 여러 겹이다

`situation` 에는 아래 세 종류의 관찰을 섞어 둔다. 어느 관찰이 어느 종류인지는 쓰지 않는다.

| 종류 | 설명 | 예 |
|---|---|---|
| 근본 원인의 흔적 | 문제를 일으킨 원인을 가리키는 관찰 | 배포 이후 특정 쿼리의 실행 계획이 바뀜 |
| 2차 증상 | 근본 원인이 다른 계층으로 번져 생긴 관찰. 가장 눈에 띄는 증상인 경우가 많다. | 커넥션 풀 고갈, 컨슈머 지연, 재시도 폭주 |
| 오해를 부르는 단서 | 같은 시각에 보여서 원인처럼 보이지만 원인이 아닌 관찰 | 같은 날 있었던 무관한 배포, 평소에도 있던 GC 로그, 한 노드의 일시적인 CPU 상승 |

- 오해를 부르는 단서도 `situation` 의 정보(시각, 범위, 수치)만으로 배제할 수 있어야 한다. 근거 없이 배제해야 하는 단서는 넣지 않는다.
- 유형별로는 다음처럼 적용한다.
  - 장애 진단, 관측성과 운영: 증상·지표·로그를 시간 순서로 주고, 근본 원인과 연쇄 증상을 가려내게 한다.
  - 데이터 정합성과 동시성: 경쟁 조건 하나에 재시도, 복제 지연, 캐시 같은 다른 계층의 동작이 겹쳐 생긴 불일치를 다룬다.
  - 성능과 확장: 한 병목을 풀면 다음 계층으로 병목이 옮겨 가는 구조로 만들고, 겉보기 병목과 실제 병목을 구분하게 한다.
  - 설계 트레이드오프, 마이그레이션과 레거시 개선: 현재 구조의 문제가 여러 계층에 걸쳐 있고, 그중 하나만 해결하는 그럴듯한 선택지가 함정이 되게 한다.
  - 코드 리뷰: 결함 중 하나 이상이 코드와 다른 계층의 설정이 만나야 드러나게 한다(예: 코드의 재시도와 Kafka 컨슈머 설정, 코드의 조회 순서와 DB 격리 수준). 문제가 없는데 의심스러워 보이는 코드도 하나 넣는다.

### 요구 항목과 채점 기준

- `requirements` 에 근본 원인, 2차 증상, 원인이 아닌 관찰을 구분하는 항목을 넣는다. 해결책은 즉시 완화와 근본 해결로 나누고, 계층마다 무엇을 바꾸는지 묻는다.
- `rubric.required` 에 다음을 넣는다. 오해를 부르는 단서를 배제하는 근거는 미들 이상에만 넣는다.
  - 근본 원인 식별
  - 근본 원인에서 2차 증상까지의 인과 연결
  - 오해를 부르는 단서를 배제하는 근거
  - 계층을 넘는 해결책
- `rubric.deductions` 에 "오해를 부르는 단서나 2차 증상만 원인으로 지목하고 그것만 고치는 답"을 넣는다.
- `keyIssues` 는 3개 이상 쓰고, 서로 다른 계층이나 서로 다른 원인을 가리키게 한다.

## 단답형 규칙

`format` 이 `short-answer` 인 문제는 용어나 한두 문장으로 답한다. 위 필드별 규칙과 다른 점은 아래와 같다.

| 필드 | 규칙 |
|---|---|
| `title` | 묻는 대상을 한 줄로 쓴다. 정답이 되는 용어를 쓰지 않는다. |
| `situation` | 질문을 쓴다. 답이 하나로 좁혀지도록 조건을 구체적으로 주고, 필요하면 수치와 설정을 넣는다. |
| `requirements` | 빈 배열로 둔다. |
| `recommendedLength` | `min` 1, `max` 150 으로 고정한다. |
| `keyIssues` | 1~2개. |
| `rubric.required` | 정확히 1개. `explanation` 에 정답, 인정하는 동의어와 대안, 부분 정답이 되는 경우를 적는다. |
| `rubric.bonus` | 빈 배열로 둔다. |
| `rubric.deductions` | 빈 배열로 둔다. 틀린 답은 `rubric.required` 판정에서 오답으로 처리한다. |
| `rubric.commonMistakes` | 1~2개. |
| `perspectives` | 빈 배열로 둔다. |
| `modelAnswer` | 정답을 먼저 쓰고, 이유를 1~3문장으로 쓴다. 소제목을 달지 않는다. |
| `relatedStudyTopics` | 2~3개. |

유형별로 다음을 묻는다.

- `term-definition`: 설명을 주고 개념의 이름을 묻는다.
- `behavior-rule`: 특정 조건에서 시스템이 어떻게 동작하는지 묻는다.
- `applied-judgment`: 짧은 상황을 주고 원인이나 조치를 하나 묻는다.

아래 품질 점검표에서 단답형은 시나리오형 복합 구조 항목을 적용하지 않는다. 대신 답이 하나로 좁혀지는지, 질문에 정답이 드러나 있지 않은지 확인한다.

## 품질 점검표

문제를 내보내기 전에 모두 확인한다.

1. **사실성:** 기술적 사실(기본값, 동작 방식, 한계 수치)이 정확한가? 확실하지 않은 수치는 쓰지 않는다.
2. **답할 수 있음:** `situation` 의 정보만으로 `requirements` 에 답할 수 있는가? 필요한 수치나 제약이 빠지지 않았는가?
3. **정답 비노출:** `title`, `situation`, `requirements` 에 정답이나 해결책 이름이 드러나지 않는가?
4. **채점 가능성:** 필수 항목이 답안에 들어 있는지 여부를 객관적으로 판단할 수 있는가? "잘 설명한다" 같은 모호한 항목이 없는가?
5. **난이도 일치:** `difficulty.md` 기준과 맞는가?
6. **유형 일치:** 유형이 묻는 능력을 실제로 묻는가? 코드 리뷰 문제에 코드가 있는가?
7. **현실성:** 실제 백엔드 서비스에서 일어날 법한 상황인가?
8. **비중복:** `existingQuestions` 의 쟁점과 겹치지 않는가?
9. **복합 구조(시나리오형):** 기술 계층이 2개 이상 얽혀 있고, 근본 원인·2차 증상·오해를 부르는 단서가 난이도 기준대로 들어 있는가? 한 계층만 고쳐서 끝나는 문제가 아닌가?

## 코드 리뷰 문제 추가 규칙

- 코드는 Kotlin(Spring) 을 기본으로 쓴다. 주제가 DB면 SQL, Kafka면 컨슈머·프로듀서 코드를 쓴다.
- 코드는 20~60줄로 쓰고, 결함은 3개 이상 숨긴다. 결함 중 하나는 운영 환경(동시성, 다중 인스턴스, 장애)에서만 드러나는 것이어야 한다.
- `situation` 에 운영 환경 정보(인스턴스 수, 재시도 정책 등)를 함께 준다.
