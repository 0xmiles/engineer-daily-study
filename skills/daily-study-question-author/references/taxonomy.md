# 분류 체계

## 형식 (`format`)

| 값 | 이름 | 설명 |
|---|---|---|
| `scenario` | 시나리오형 | 구체적인 실무 상황을 주고 판단·설계·진단을 요구한다. |
| `concept` | 개념형 | CS·아키텍처 개념의 원리와 그 원리가 실무에 주는 의미를 서술하게 한다. |

## 유형 (`category`)

`format` 이 `scenario` 이면 시나리오 유형 7개 중 하나, `concept` 이면 개념 유형 5개 중 하나를 쓴다.

### 시나리오 유형

| 값 | 이름 | 묻는 능력 |
|---|---|---|
| `incident-diagnosis` | 장애 진단 | 증상에서 가설을 세우고, 조사 순서를 정하고, 즉시 완화책과 근본 해결책을 구분하는 능력 |
| `design-tradeoff` | 설계 트레이드오프 | 선택지를 비교하고, 제약 안에서 결정하고, 결정의 근거를 설명하는 능력 |
| `consistency-concurrency` | 데이터 정합성과 동시성 | 경쟁 조건, 멱등성, 분산 트랜잭션, 이중 쓰기를 다루는 능력 |
| `performance-scaling` | 성능과 확장 | 병목을 찾고, 용량을 추정하고, 단계별로 확장하는 능력 |
| `migration-legacy` | 마이그레이션과 레거시 개선 | 서비스를 멈추지 않고 전환하고, 롤백 전략을 세우는 능력 |
| `code-review` | 코드 리뷰 | 코드에 숨은 결함과 운영 위험을 읽어 내는 능력. 반드시 `situation` 에 코드 블록을 넣는다. |
| `observability-operations` | 관측성과 운영 | 지표·알람·SLO를 설계하고 장애 대응 체계를 만드는 능력 |

### 개념 유형

| 값 | 이름 | 묻는 능력 |
|---|---|---|
| `principle` | 원리 설명 | 개념의 동작 방식을 정확하게 설명하는 능력 |
| `why` | "왜" 질문 | 설계가 그렇게 된 이유를 설명하는 능력 |
| `comparison` | 비교 | 비슷한 개념의 경계와 선택 기준을 구분하는 능력 |
| `cross-layer` | 계층 관통 | 여러 계층(애플리케이션, 런타임, OS, 네트워크, 저장소)을 연결해서 설명하는 능력 |
| `architecture-principle` | 아키텍처 원칙 | 원칙(CAP, 결합도, 멱등성 등)과 실제 적용 사이의 간극을 설명하는 능력 |

## 스택 주제 (`topic`)

| 값 | 이름 | 시나리오에서 다룰 상황 | 개념에서 다룰 원리 |
|---|---|---|---|
| `kotlin-spring` | Kotlin/Spring | 트랜잭션이 적용되지 않는 버그, JPA N+1, 커넥션 풀 고갈, 코루틴과 블로킹 호출 | `@Transactional` 프록시, 트랜잭션 전파, 영속성 컨텍스트, 코루틴과 스레드 모델, Bean 생명주기 |
| `kafka` | Kafka | 이벤트 유실과 중복, 컨슈머 지연, 리밸런싱 폭주, 순서 역전, 포이즌 메시지 | 파티션과 순서 보장, 오프셋 커밋, 복제와 ISR, exactly-once의 범위, 컨슈머 그룹 |
| `mysql-postgresql` | MySQL/PostgreSQL | 데드락, 슬로우 쿼리, 무중단 스키마 변경, 테이블 비대화, 복제 지연 | MVCC, 격리 수준, 인덱스 구조, 실행 계획, 락 종류, WAL·redo log |
| `dynamodb` | DynamoDB | 핫 파티션, 쓰로틀링, 접근 패턴 변경, GSI 지연, 대용량 스캔 | 파티션 키 설계, 단일 테이블 설계, 일관성 모델, 조건부 쓰기, 트랜잭션 API |
| `distributed-systems` | 분산 시스템 공통 | 재시도 폭주, 멱등성, 서비스 간 정합성, 분산 락, 시계 문제 | CAP·PACELC, Saga, 합의, 전달 보장 수준, 타임아웃과 장애 감지 |
| `cache` | 캐시 | 캐시 스탬피드, 캐시와 DB 불일치, 핫 키, 메모리 고갈과 축출 | 캐시 전략(cache-aside, write-through 등), 만료와 무효화, 로컬·분산 캐시 |
| `api-architecture` | API와 아키텍처 | 하위 호환을 깨는 변경, 모놀리스 분리, 동기 호출 연쇄 장애, 페이지네이션 | 동기·비동기 결합도, 모듈 경계, API 버전 관리, 멱등 키, 백프레셔 |

Redis, SQS, Elasticsearch 같은 주변 기술은 위 주제의 상황 안에서 자연스럽게 등장해도 된다.

### 사용자 정의 주제

사용자는 앱에서 주제를 직접 추가할 수 있다(예: Redis, Elasticsearch). 이런 주제의 `topic` 값은 `custom-` 으로 시작하고, 요청에 `customTopic` 이 함께 온다.

- `customTopic.label` 은 주제 이름, `customTopic.description` 은 사용자가 적은 출제 범위다.
- 위 표 대신 `description` 의 범위 안에서 시나리오 상황과 개념 원리를 고른다. 범위를 벗어난 쟁점을 주로 묻지 않는다.
- 결과의 `topic` 에는 요청의 `topic` 값을 그대로 쓴다.
- `customTopic` 이 `null` 이면 위 표의 기본 주제다.
